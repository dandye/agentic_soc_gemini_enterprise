Coordinated Agent-to-Agent SOC System

Welcome to the expert documentation site for the **Agentic Security Operations Center (SOC) System**. This project implements a state-of-the-art **Multi-Agent Network** built with the Google Vertex AI Agent Development Kit (ADK).

Unlike traditional security automation platforms, this system coordinates five specialized, autonomous AI agents deployed on Google Cloud Platform. These agents communicate seamlessly via regional gRPC tunnels to perform deep security investigations, threat hunt across active telemetry, formulate SIEM detection rules, and isolate compromised endpoints in real-time.

💡
Key Benefit: By splitting capabilities into a coordinated network of specialists, the system avoids context-bloat and latency bottlenecks, ensuring that each task is handled by the model best suited for it (e.g., lightweight models for fast scanning, reasoning-heavy models for coordination).

Multi-Agent A2A Network

The core architecture utilizes a **Coordinated Agent-to-Agent (A2A)** routing paradigm. The Orchestrator manages the user session and delegates tasks to remote specialists.

Agent Profiles & Responsibilities

Orchestrator & Tier 1 SOC Analyst

The Orchestrator is the main interface. It receives the user's natural language requests, triages incoming security alerts, and delegates complex research or mitigation tasks to specialist agents.

It hosts an in-process **Tier 1 SOC Analyst** sub-agent that executes rapid triaging on SIEM alerts and leverages the **Elasticsearch Grounding Index** to query playbooks and static runbooks.

CTI Researcher (Cyber Threat Intelligence)

The CTI Researcher is a specialist in threat profiling. It researches threat actors, analyzes malware families (e.g. ransomware, beaconing agents), and builds actor profiles using direct access to **Google Threat Intelligence (VirusTotal)**.

Threat Hunter & Detection Engineer

The Threat Hunter proactively scans SIEM logs using **Chronicle UDM Search** to locate Indicators of Compromise (IOCs). It compiles complete security event timelines and maps threat actor traversal using **Neo4j Graph Queries**.

The Detection Engineer translates these threat timelines and TTPs directly into **YARA-L SIEM detection rules** and deploys them to Chronicle, validating their coverage against historical logs.

Tier 2 Incident Responder

The Tier 2 Responder is the containment specialist. It is the only agent with direct access to SOAR containment playbooks and active mitigation endpoints. It can isolate compromised endpoints, block malicious domains, disable compromised credentials, and coordinate active host containment.

Getting Started

To get started with local development, testing, and cloud deployments, you must first initialize your virtual environment and resolve the package dependencies.

⚠️
Mac & Airlock Developers: If your machine resides behind a corporate Airlock proxy, your package installations may fail with 401 Unauthorized errors. You must bypass the private registry lock by instructing pip to fetch directly from the public PyPI index. 
# Create and activate your python virtual environment
python3 -m venv .venv
source .venv/bin/activate

# Install dependencies directly from the public PyPI index to bypass Airlock locks
pip install --index-url https://pypi.org/simple -r requirements.txt

Environment Configuration

All agents and CLI tools load their configurations from a local .env file (which is git-ignored for safety). Copy the example template and fill in your coordinates: 

cp .env.example .env

The environment is configured in stages:

Stage 1: Google Cloud & Chronicle Prerequisites

Set these variables in your .env before deploying any agents:

  • GCP_PROJECT_ID: Your Google Cloud Project ID (e.g. secops-demo-env).
  • GCP_LOCATION: GCP region for Reasoning Engines (e.g. us-east4).
  • CHRONICLE_CUSTOMER_ID: Your Chronicle SIEM Customer UUID.
  • CHRONICLE_SERVICE_ACCOUNT_PATH: Path to your Chronicle service account JSON credentials.
Stage 2: Grounding & Graph Database VM Configuration

Set these variables to connect the agents directly to your telemetry databases:

  • ELASTICSEARCH_GROUNDING_ENABLED: Set to True to route runbook searches directly to Elasticsearch.
  • ELASTICSEARCH_URL: Elasticsearch API URL (e.g. http://${ELASTICSEARCH_VM_IP}:9200).
  • ELASTICSEARCH_USER / ELASTICSEARCH_PASSWORD: Elasticsearch credentials.
  • NEO4J_URI: Neo4j Bolt connection URI (e.g. bolt://${NEO4J_VM_IP}:7687).
  • NEO4J_USER / NEO4J_PASSWORD: Neo4j credentials.

Telemetry Database Grounding

To make your AI agents extremely intelligent, the Orchestrator and CTI Researcher use two distinct database grounding methods:

Elasticsearch Runbook Grounding

When the agent needs to find a playbook, incident response plan (IRP), or security guideline, it queries your GCE Elasticsearch VM directly over HTTP port `9200`. This completely bypasses traditional vector databases, allowing the agent to run high-performance full-text searches across **3,405 document chunks**.

Neo4j Security Operations Knowledge Graph

When the threat hunter or orchestrator needs to traverse complex threat relationships (e.g., finding all hosts logged into by a compromised user, or identifying all alerts triggered by a specific file hash), it queries a live Neo4j Graph Database VM over the **Bolt protocol (port 7687)**.

Knowledge Graph Ingestion

Your local telemetry and Chronicle investigations are compiled into a flat JSON knowledge graph located at: harvested_investigations/knowledge_graph.json.

To populate the live GCE Neo4j VM with this telemetry, you must run the graph ingestion command. This will connect to the database, set up uniqueness constraints, and upload **1,148 nodes and 7,789 edges** in batches. 

# Run the Neo4j connection test
just neo4j-test

# Ingest the flat knowledge graph JSON into Neo4j
just neo4j-ingest

CLI Command Reference

This project features a **Dual CLI Interface** with identical functionality. You can manage deployments and databases using either the traditional justfile or the unified, type-safe Python CLI (manage.py).

Search or click the tabs below to view the command references: 

# ---- AGENT ENGINE DEPLOYMENTS ----
just agent-engine-deploy               # Deploy Orchestrator agent
just agent-engine-update               # In-place update of agent code (retains session)
just agent-engine-test query="T1003"   # Test deployed agent with a natural language query

# ---- ELASTICSEARCH GROUNDING ----
just elastic-info                      # Show statistics about the Elasticsearch grounding index
just elastic-sync                      # Sync local runbooks into Elasticsearch
just elastic-search query="ransomware" # Query the Elasticsearch index directly

# ---- NEO4J GRAPH DATABASE ----
just neo4j-test                        # Test Bolt connection to Neo4j VM
just neo4j-ingest                      # Upload knowledge_graph.json to Neo4j
just neo4j-clear                       # Delete all data (nodes & edges) from Neo4j
# ---- AGENT ENGINE DEPLOYMENTS ----
python manage.py agent-engine deploy   # Deploy Orchestrator agent
python manage.py agent-engine update   # In-place update of agent code
python manage.py agent-engine test     # Send test query to deployed agent

# ---- ELASTICSEARCH GROUNDING ----
python manage.py elastic info          # Show stats about the Elasticsearch index
python manage.py elastic sync          # Sync runbooks
python manage.py elastic search         # Query the index

# ---- NEO4J GRAPH DATABASE ----
python manage.py neo4j test-connection # Test connection to Neo4j VM
python manage.py neo4j ingest          # Ingest knowledge graph
python manage.py neo4j clear           # Delete all data in Neo4j database

Troubleshooting & Tips

Authentication Exception: missing credentials for REST request

If you encounter a 401 security_exception when running just elastic-info:

  1. Verify that your .env file has ELASTICSEARCH_USER=elastic and the correct password configured.
  2. Ensure the GCE VM firewall allows incoming TCP traffic on port 9200.
Neo4j Service Unavailable: Failed to establish connection

If just neo4j-test fails to connect:

  1. Check that the GCE VM external IP matches the NEO4J_URI in your .env file.
  2. Verify that your GCP Firewall rule allow-neo4j-bolt is active and allows incoming TCP traffic on ports 7687 (Bolt) and 7474 (Web Console).
ReasoningEngine deployment fails with gRPC mismatches

If the Orchestrator fails to route tasks to specialists with region errors:

  1. Ensure that all specialists (CTI, Threat Hunter, Detection Engineer) are deployed in the correct GCP region.
  2. Verify that GCP_LOCATION in your .env file is set to the native region of the Orchestrator (e.g. us-east4) during updates.
